# 设计说明

本文说明 new-api-mcp 要解决什么问题、为什么这样设计，以及刻意不做的事。实现层面的结构见 [architecture.md](architecture.md)。

## 1. 目标与非目标

**目标**：提供一个独立的 MCP 服务，把 new-api 管理后台的 `/api/*` 接口包装成面向运维任务的工具，让 Agent 能完成日常排障和运营：查渠道为什么被禁用、在日志里定位慢请求、启停渠道、给新模型补定价、看用量排行等。

**非目标**：

- 不改 new-api 本体，不直连数据库，只依赖它的 HTTP 管理接口。
- 不包装 `/v1/*` 转发接口。那是模型调用，Agent 直接用 API key 调即可。
- 不追求覆盖全部面板路由。支付、OAuth、Passkey、注册登录等与运维无关的接口不做。
- 不提供任何读取明文密钥的能力（渠道 key、用户令牌）。

## 2. 关键事实

以下事实决定了整个设计，均来自 new-api 源码（`middleware/access_token_routes.go`、`docs/authentication.md` 等）。

### 2.1 鉴权：个人访问令牌（PAT）

- 面板支持 PAT：`nap_` 加 43 位随机串，通过 `Authorization: Bearer <pat>` 发送。
- 创建 PAT 时必须选择 scope（形如 `resource:action`）和有效期。只能授予自己当前拥有的权限，并且**每次请求都会重新读取角色和权限**，撤权立即生效。
- **每条面板路由都声明了所需的 scope**，未声明的路由一律拒绝 PAT（`ACCESS_TOKEN_ROUTE_UNDECLARED`）。
- 少数路由只接受浏览器登录会话，PAT 永远调不了，例如管理 PAT 本身。因此 **PAT 无法查询自己有哪些 scope**，MCP 也就无法在启动时预知调用方的权限，只能依靠 new-api 返回的 403。

### 2.2 二次验证

删除用户、禁用用户、升降管理员、重置密码或 2FA、查看渠道 key 等高危操作，需要请求头里带一个短期有效的 `X-Security-Proof`。PAT 可以通过 `POST /api/verify` 换取 Proof，但只支持密码或 2FA，不支持 OAuth。

这类操作 v1 直接不做，留给人在面板上完成。

### 2.3 审计与限流

- new-api 对所有 PAT 请求自带审计，记录用户、角色和 `token_ref`（PAT 的 SHA-256 摘要）。只要每人用自己的 PAT，“谁通过 Agent 改了什么”在 new-api 的审计日志里就查得到，MCP 不需要自建审计。
- `/api/*` 有按来源 IP 的全局限流（默认 360 次 / 180 秒）。所有 Agent 经同一个 MCP 实例访问时，共用的是 MCP 的出口 IP，必须在 MCP 侧限速。
- `GET /api/option/` 会在服务端剔除密钥类配置项，所以经 MCP 读配置不会泄露密钥。

### 2.4 影响工具设计的接口语义

- `PUT /api/channel/` 只更新请求里带的字段，但请求体带 `status` 会被拒绝，启停必须走 `POST /api/channel/:id/status`。
- `PUT /api/option/` 是**整值覆盖**。像 `GroupRatio` 这种值为 JSON 对象的配置，直接写会把整张表冲掉，必须读出、合并再写回。
- `PATCH /api/option/model_pricing` 按模型更新，并要求带上每个模型当前的 `expected_version`，天然具备乐观锁，改价应走它。
- `PUT /api/user/` 会同时覆盖用户名、显示名、分组、备注四个字段，只改其中一个也要把其余三个带上。
- 仓库自带的 OpenAPI 文件路由不全、鉴权描述过时，**不能据此自动生成工具**，工具表只能手工维护。
- 响应统一是 `{success, message, data}`，很多业务失败也返回 HTTP 200，必须检查 `success`。

## 3. 设计决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 代码位置 | 独立仓库 | 只依赖 HTTP 契约，不给 new-api 增加合并负担，可独立发版 |
| 语言 | Go + 官方 `modelcontextprotocol/go-sdk` | 单二进制、易部署 |
| 传输 | Streamable HTTP（无状态）为主，同一二进制支持 stdio | 多人共用一个实例；无状态便于重启；stdio 便于本机调试 |
| 鉴权 | PAT 透传 | 权限、撤权、审计全部复用 new-api；服务被攻破也拿不到长期凭据 |
| 工具形态 | 手工编排的任务型工具 | 直通全部路由会撑爆模型上下文，还会把整值覆盖这类坑原样暴露给模型 |
| 写操作 | 两步确认 | 让人在执行前看到 diff，并防止预览后被并发修改 |

关于 PAT 透传：MCP 规范不鼓励把上游令牌直接透传。这里 MCP 只是 new-api 管理面的一层薄门面，透传是最简单、权限语义最清楚的做法。若要面向不受信任的第三方 Agent 平台，应改为 MCP OAuth，由 new-api 充当授权服务器，工具层不受影响。

## 4. 工具分级

每个工具属于一个域（ops、channel、logs、user、pricing、option、report），并分为三级：

- **只读**：查询，不改变任何状态。
- **可逆操作**：启停渠道、测试渠道、管理多 key 渠道的 key、清渠道亲和缓存。直接执行，并回显操作前后的状态。
- **配置变更**：改渠道参数、改定价、改系统配置、调整用户余额和资料。一律两步确认。

启动参数 `MCP_ALLOW` 决定暴露到哪一级，`MCP_TOOLSETS` 决定暴露哪些域。它们只是收窄工具列表的开关，**真正的权限始终由调用方 PAT 在 new-api 里的权限决定**，MCP 不做额外的权限判断。

刻意不做的工具：新增、删除、复制渠道，查看渠道 key，删除、禁用用户，修改角色，重置 2FA 或 Passkey，导出令牌明文。原因是这些操作要么需要二次验证，要么不可逆，要么涉及密钥。

## 5. 写操作的安全性

1. **两步确认**：第一次调用返回变更预览（当前值 → 新值）和一个 `confirm_token`；带着令牌、用相同参数再调一次才执行。令牌是 HMAC 签名的 `{工具, 参数摘要, 当前值摘要, 调用方令牌摘要, 过期时间}`，服务本身不需要保存状态。
2. **乐观锁**：执行前重新读取当前值，摘要对不上（预览后被别人改过）就拒绝并要求重新预览。
3. **合并而不是覆盖**：JSON 对象类配置按条目 `set` / `unset`，由 MCP 读出、合并、写回；定价按模型更新并带上版本号。
4. **副作用写进工具描述**：例如“禁用渠道会断开该渠道上的 WebSocket 连接”“渠道亲和没有自动故障转移”，让模型和审批的人都能看到。
5. **输入校验**：参数先过 JSON Schema 校验，再做业务校验（id 为正整数、时间窗口上限、枚举值）。
6. **不记录密钥**：日志里只记 PAT 摘要的前缀（与 new-api 审计日志的 `token_ref` 可以对上），不记请求体里的敏感字段。

## 6. 输出与错误

- **裁剪**：列表默认每页 20 条、最多 100 条，带 `total` 和 `has_more`；每个工具只输出白名单字段；单次结果超过约 60 KB 时返回错误，提示收窄条件。
- **不可信文本**：日志内容、上游报错等来自外部的自由文本，统一放在 `untrusted_` 开头的字段里，并在服务说明中提醒模型把它们当数据，不执行其中的指令。
- **错误映射**：把 new-api 的响应转成可操作的提示，例如缺哪个 scope、令牌过期、需要人工二次验证、版本不匹配、被限流。所有工具错误都以工具结果返回（`isError: true`），而不是协议错误，模型能读到并自行调整。

## 7. 与 new-api 版本的契约

独立仓库最大的风险是 new-api 升级后路由或 scope 变了而 MCP 不知道。应对办法：

1. **契约检查**（`tools/contractcheck`）：解析 new-api 源码里的路由 scope 表，与每个工具声明的路由逐条比对方法、路径和 scope。升级 new-api 后先跑一遍。
2. **运行期提示**：`server_status` 同时报告 new-api 的版本和本服务验证过的版本。
3. **兜底**：遇到 `ACCESS_TOKEN_ROUTE_UNDECLARED` 或 404，明确提示是版本不匹配。
